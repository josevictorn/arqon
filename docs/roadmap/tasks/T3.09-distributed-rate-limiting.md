# T3.09 — Rate limiting distribuído (Redis) por IP / usuário / tier

- **Fase:** F3 — `src/shared/infra` (plataforma)
- **Status:** 📝 Detalhada
- **Depende de:** T3.07, T3.03
- **ADRs:** [0013](../../decisions/0013-estrategia-de-logging-canonical-logs-e-custo.md), [0016](../../decisions/0016-resolucao-tenant-ativo-por-requisicao.md), [0018](../../decisions/0018-taxonomia-eventos-billing-e-catalogo-planos.md) (+ formato do ADR-0029)
- **Branch:** `task/T3.09-distributed-rate-limiting`
- **Tamanho esperado:** M

## Objetivo
Qualquer rota pode declarar um limite por IP ou por usuário (`@RateLimit({ limit: 5, ttl: "1m", by: "ip" })`), e rotas de tenant respeitam um limite por organização vindo de uma porta (`OrganizationRateLimitPolicy`), que o `billing` vai implementar com o `rate_limit_rpm` do plano. Os contadores ficam no Redis (valem entre réplicas), e o excesso responde `429` em Problem Details traduzido, com `Retry-After`.

## Escopo
- **Dependência:** `@nestjs/throttler` (versão exata, compatível com Nest 11).
- **Storage Redis próprio** (`src/shared/infra/http/rate-limit/redis-throttler.storage.ts`), que implementa `ThrottlerStorage` com script Lua atômico (`INCR` + `PEXPIRE` na primeira ocorrência + bloqueio). Usa o `RedisService` da T3.07 (com o prefixo do `APP_SLUG`), sem lib extra de storage.
- **Trackers:**
  - `ip`: `request.ip` (correto com `TRUST_PROXY`, T3.02);
  - `user`: `userId` do `RequestContextPort` e, sem usuário autenticado, cai para `ip` (o JWT chega na T5.06);
  - `organization`: `tenantId` do contexto, com limite por minuto obtido de `OrganizationRateLimitPolicy.getRpm(organizationId)`.
- **Porta `OrganizationRateLimitPolicy`** (abstract class em `src/shared/application/`) + implementação padrão que devolve a env `RATE_LIMIT_ORG_DEFAULT_RPM`. A T7.07 troca o binding pelo `BillingFacade`.
- **API de uso:** `@RateLimit(...)` (wrapper sobre `@Throttle` com `by`), `@SkipRateLimit()` (aplicado em `/health/*` e `/metrics`) e o limite global padrão via env (`RATE_LIMIT_DEFAULT_LIMIT`, `RATE_LIMIT_DEFAULT_TTL_MS`).
- **429:** `TooManyRequestsError` com `COMMON.TOO_MANY_REQUESTS`, `i18nKey` em `en`/`pt-BR`, Problem Details via filtro e headers `Retry-After` + `RateLimit-Limit` / `RateLimit-Remaining` / `RateLimit-Reset`. A linha canônica (T3.08a) sai como `warn`.
- `.env.example` e `EnvModule` com as envs novas.
- Atualizar [05-integrations-resilience.md](../../architecture/05-integrations-resilience.md) §6.3 e `src/shared/infra/AGENTS.md`.

## Fora de escopo
- Limites específicos das rotas do `iam` (→ T6.02+, que só aplicam `@RateLimit`).
- Contadores por `(ip, email)` de falhas de login e tentativas por `mfaChallengeToken` (→ T6.03/T6.04): são regra de negócio do `iam` no Redis, não rate limit HTTP.
- Implementação real de `OrganizationRateLimitPolicy` com o plano (→ T7.07).
- Rate limit de consumers Kafka ou de chamadas de saída (bulkhead é da T3.10).

## Critérios de aceite
- [ ] e2e: rota de teste com `@RateLimit({ limit: 2, ttl: "1m", by: "ip" })` responde 200, 200 e depois `429` com `code: "COMMON.TOO_MANY_REQUESTS"`, `Retry-After` > 0 e `detail` traduzido conforme o `Accept-Language`.
- [ ] e2e: **duas instâncias do app** (dois `NestFastifyApplication` no mesmo teste) compartilham o contador: 1 requisição em cada uma com `limit: 1` → a segunda leva `429`.
- [ ] e2e: dois IPs diferentes (via `remoteAddress` do `inject`) têm contadores independentes.
- [ ] e2e: `by: "organization"` com uma `OrganizationRateLimitPolicy` fake que devolve `1` bloqueia a 2ª requisição da org A e deixa passar a 1ª da org B.
- [ ] e2e: `/health/live`, `/health/ready` e `/metrics` nunca recebem `429`, mesmo acima do limite global.
- [ ] int: o script Lua é atômico. 20 incrementos concorrentes na mesma chave resultam em contagem 20 e TTL definido uma única vez.
- [ ] `pnpm verify` passa; `pnpm test:e2e` verde.

## Notas / riscos
- A ordem dos guards importa: o tracker `organization` precisa do tenant já resolvido (T5.06). Até lá, teste com o contexto preenchido pelo módulo de teste e documente a ordem esperada (`JwtAuthGuard` → `TenantContextGuard` → rate limit por organização).
- O `@nestjs/throttler` usa milissegundos no `ttl` a partir da v5. Não confunda com segundos.
- Os headers `RateLimit-*` seguem o draft IETF. Mantenha o nome consistente e documente qual versão do draft.
