## Objetivo
Qualquer módulo consegue declarar um Integration Event com **um único** schema Zod (`defineIntegrationEventContract`) e ganhar de uma vez: tipo estático do payload e do envelope, validação em memória, nome de tópico/DLQ derivado da convenção e a garantia de que o schema converte para JSON Schema (pré-requisito da T4.02). O envelope tem exatamente os campos do ADR-0019.

## Escopo
- **Dependência:** adicionar `zod` 4.x (versão exata, conforme [ADR-0003](../../decisions/0003-runtime-versoes-e-package-manager.md)) em `dependencies`.
- **`src/shared/core/events/integration-event.ts`** (TypeScript puro, **sem Zod**):
  - constante `ACTOR_TYPES = ['USER', 'SYSTEM', 'WEBHOOK', 'ANONYMOUS'] as const` e `ActorType` derivado dela (`(typeof ACTOR_TYPES)[number]`);
  - `EventActorMetadata` e `IntegrationEventEnvelope<TPayload>` com **exatamente** os campos do ADR-0019 (`eventId`, `eventName`, `schemaVersion`, `aggregateId`, `aggregateVersion`, `occurredAt`, `tenantId`, `correlationId`, `traceparent`, `actor`, `payload`), todos `readonly`;
  - `NewIntegrationEvent<TPayload>`: o que o Command informa (`eventName`, `aggregateId`, `aggregateVersion`, `payload`); o resto é preenchido pelo `UnitOfWork` via ALS na T3.05.
- **`src/shared/core/events/event-name.ts`** (TypeScript puro):
  - validação da convenção `<context>.<aggregate>.<action>.v<N>` (segmentos `[a-z][a-z0-9_]*`, `N ≥ 1`), aceitando os nomes já catalogados, como `iam.mfa.email_otp_requested.v1` e `notifications.notifications.all_read.v1`;
  - `parseEventName(name): Either<InvalidEventNameError, { context, aggregate, action, version }>`;
  - `topicFor(eventName)` (tópico = `eventName`) e `dlqTopicFor(topic)` (`<topic>.dlq`).
- **`src/shared/contracts/events/integration-event-envelope.schema.ts`** (Zod, ADR-0024):
  - `eventActorSchema` (com `z.enum(ACTOR_TYPES)` importado do `core`) e `integrationEventEnvelopeSchema(payloadSchema)`, ambos com `.readonly()` para que o tipo inferido tenha os mesmos modificadores da interface;
  - **teste de tipo** no spec: `expectTypeOf<z.infer<typeof schema>>().toEqualTypeOf<IntegrationEventEnvelope<Payload>>()`, checado pelo `pnpm typecheck`.
- **`src/shared/contracts/events/define-integration-event-contract.ts`** (Zod, ADR-0024):
  - reaproveita `integrationEventEnvelopeSchema`, apertando só o `eventName` para `z.literal(eventName)`;
  - `defineIntegrationEventContract({ eventName, schemaVersion, payloadSchema })`, onde `payloadSchema` é obrigatoriamente `z.object(...)`;
  - devolve um contrato imutável com `eventName` (literal), `schemaVersion`, `topic`, `dlqTopic`, `payloadSchema`, `envelopeSchema` (Zod do envelope completo: `eventId`/`aggregateId` como UUIDv7, `occurredAt` ISO 8601 UTC, `eventName` literal, `schemaVersion` como `z.number().int().min(1)` (nunca literal, ADR-0023), `actor` etc.) e `parse(input)` devolvendo `Either` (sem lançar);
  - `schemaVersion` **não** precisa ser igual ao `N` do `.vN` (ADR-0023): `eventName: '…v1'` com `schemaVersion: 3` é válido;
  - utilitários de tipo `IntegrationEventPayload<C>` e `IntegrationEventOf<C>` (= `IntegrationEventEnvelope<IntegrationEventPayload<C>>`);
  - **falha rápida na definição** (erro de programação, lançado no carregamento do módulo): `eventName` fora da convenção, `schemaVersion` não inteiro ou `< 1`, ou `payloadSchema` não conversível para JSON Schema (`z.toJSONSchema` lança para `z.date()`, `z.bigint()`, `z.map()` etc., o que faz valer a regra do ADR-0020 de "só tipos serializáveis em JSON").
- **`test/architecture/zod-boundaries.spec.ts`** (Opção C pontual do ADR-0010, sem alterar o `.dependency-cruiser.cjs`): varre os imports e falha se algum arquivo em `src/shared/core/**` importar `zod` ou se algum `src/**/domain/**` importar `src/shared/contracts/events/**`. Inclui um caso que prova que o teste detecta a violação (fixture em memória ou em `test/architecture/fixtures/`).
- Testes (`*.spec.ts`): envelope válido passa em `parse`; `eventId` UUIDv4, `occurredAt` sem fuso, `eventName` diferente do contrato e `actorType` desconhecido falham; teste de tipo de `IntegrationEventPayload<C>`; nomes válidos/inválidos da convenção; `payloadSchema` com `z.date()` faz a definição lançar.
- **Docs:** em [docs/events/catalog.md](../../events/catalog.md), um exemplo curto de contrato com `defineIntegrationEventContract` (o [02-directory-structure.md](../../architecture/02-directory-structure.md) já foi atualizado pelo ADR-0024).

## Critérios de aceite
- [ ] Um teste de tipo prova que `IntegrationEventEnvelope` tem exatamente as chaves do ADR-0019: adicionar ou remover um campo quebra o teste.
- [ ] ADR-0024: um teste de tipo prova que `z.infer` do schema Zod do envelope é **idêntico** a `IntegrationEventEnvelope` (adicionar um campo só num dos lados, ou trocar `.nullable()` por `.optional()`, quebra o `pnpm typecheck`).
- [ ] ADR-0024: `test/architecture/zod-boundaries.spec.ts` passa no repositório e prova, com um caso de violação, que detecta `zod` em `shared/core` e `domain/` importando `shared/contracts/events`.
- [ ] `ACTOR_TYPES` é a única lista de `actorType`: o schema Zod usa `z.enum(ACTOR_TYPES)`, sem repetir os valores.
- [ ] `pnpm arch:check` segue verde.
- [ ] `defineIntegrationEventContract` com `eventName: 'billing.invoice.paid.v1'` gera `topic === 'billing.invoice.paid.v1'` e `dlqTopic === 'billing.invoice.paid.v1.dlq'`.
- [ ] `defineIntegrationEventContract` lança na definição para `eventName: 'BillingInvoicePaid'`, `schemaVersion: 0` e para `payloadSchema` com `z.date()`.
- [ ] `contract.parse(envelope)` devolve `Right` para um envelope válido e `Left` (sem lançar) para cada caso inválido listado no Escopo.
- [ ] ADR-0023: um contrato `billing.invoice.paid.v1` com `schemaVersion: 3` é aceito na definição, e o `parse` dele aceita envelopes com `schemaVersion` 1, 2 e 3 (revisões anteriores) e rejeita `0` e `1.5`.
- [ ] O JSDoc de `defineIntegrationEventContract` explica a regra do `schemaVersion` (sobe `+1` a cada mudança compatível e recomeça em `1` em cada novo `.vN`), com link para o ADR-0023.
- [ ] `z.toJSONSchema(contract.envelopeSchema)` roda sem erro para o contrato de exemplo do teste.
- [ ] 100% de cobertura em `src/shared/core/**`; `pnpm verify` passa.

## Notas / riscos
- **Onde fica o Zod está decidido no [ADR-0024](../../decisions/0024-zod-fora-do-shared-core.md):** só tipos e `ACTOR_TYPES` em `src/shared/core/events/`; schema Zod do envelope e helper em `src/shared/contracts/events/`. Não derive a interface com `z.infer` (regra 2 do ADR).
- **`schemaVersion` × `.vN` está decidido no [ADR-0023](../../decisions/0023-semantica-de-schema-version.md):** `.vN` é o major do tópico; `schemaVersion` é a revisão compatível dentro dele. O snapshot de JSON Schema que detecta um `schemaVersion` esquecido é da **T4.02**, não desta task.
- `z.uuid({ version: "v7" })` e `z.iso.datetime()` são APIs do Zod 4. Não use as do Zod 3 (`z.string().uuid()` aceita qualquer versão).
- `tenantId` é `string | null`. Eventos globais do `iam` usam `null` (ADR-0019), e o `envelopeSchema` precisa aceitar isso.
- Lançar no `defineIntegrationEventContract` é aceitável: é erro de programação detectado no carregamento, não erro de negócio (`Either` continua obrigatório em `parse`).
