## Objetivo
Um Command executa `uow.execute(work)` e, numa única transação PostgreSQL: o tenant ativo é aplicado com `set_config('app.current_tenant_id', …, true)`; os repositórios usam o `tx` sem recebê-lo como parâmetro; os Domain Events dos agregados rastreados são despachados (inclusive os gerados pelos próprios handlers); os Integration Events viram linhas de `outbox_events` com o envelope do ADR-0019 preenchido a partir do contexto; e um `pg_notify('outbox_new_event', '')` só é entregue após o `COMMIT`. Qualquer falha desfaz tudo.

## Perguntas que bloqueiam (viram o ADR-0030)
1. **Obrigatoriedade** (ponto aberto do ADR-0025): todo Command que altera agregado passa por `uow.execute`, ou só os que têm mais de um agregado ou Integration Event? **Recomendação:** todo Command que altera agregado, para ter um caminho só e nenhum Domain Event perdido.
2. **`Left` dentro do `execute`:** se o `work` devolve `left(...)`, há commit ou rollback? **Recomendação:** rollback. O `execute` é tipado como `execute<L, R>(work: () => Promise<Either<L, R>>): Promise<Either<L, R>>`, desfaz a transação em `Left` e devolve o mesmo `Left`.
3. **Versão e concorrência otimista:** quem incrementa `aggregate.version` e como o conflito chega ao use case? **Recomendação:** o repositório faz `UPDATE … WHERE id = $1 AND version = $expected` e `version + 1`; 0 linhas afetadas lança `OptimisticLockException` (infra), que o `UoW` converte em `left(ConcurrencyError)`. O `aggregateVersion` do envelope é a versão **após** o save.
4. **Assinatura de `addIntegrationEvent`:** como o `schemaVersion` chega ao envelope, já que o `NewIntegrationEvent` da T2.05 não o tem? **Recomendação:** `addIntegrationEvent(contract, { aggregateId, aggregateVersion, payload })`. O `UoW` valida o `payload` com `contract.payloadSchema` (falha = erro de programação → rollback) e usa `contract.schemaVersion`.
5. **`execute` aninhado:** **Recomendação:** junta-se à transação externa (sem *savepoint*) e só o nível mais externo faz commit.

## Escopo
- **`src/shared/application/unit-of-work.ts`**: abstract class `UnitOfWork` com `execute`, `track(aggregate)` e `addIntegrationEvent`, conforme o ADR-0030.
- **`src/shared/infra/database/prisma/prisma-unit-of-work.ts`**:
  - abre `prisma.$transaction` interativa e guarda o `tx` num `AsyncLocalStorage` próprio. O getter `PrismaService.client` passa a devolver o `tx` ativo ou o client raiz;
  - `SELECT set_config('app.current_tenant_id', $1, true)` no início, com o `tenantId` do contexto, ou `'SYSTEM_BYPASS'` quando `actor.actorType === "SYSTEM"`. Sem tenant e sem `SYSTEM`, não define nada, e a policy nega por padrão;
  - após o `work`: laço `dispatcher.dispatchFor(aggregate)` sobre os agregados rastreados até não haver eventos pendentes (com limite de iterações que lança erro de programação, para evitar laço infinito);
  - monta o envelope de cada Integration Event (`eventId` via `UniqueEntityID`, `occurredAt` ISO UTC, `tenantId`, `correlationId` e `actor` do `RequestContextPort`, `traceparent` via `propagation.inject` do `@opentelemetry/api`, `null` se não houver span), valida com `contract.envelopeSchema` e insere em `outbox_events` (`topic = eventName`, `event_version = schemaVersion`, `headers` com as chaves do ADR-0019);
  - um único `SELECT pg_notify('outbox_new_event', '')` por transação com eventos;
  - commit, ou rollback em exceção ou `Left`.
- **Provider singleton de `DomainEventDispatcher`** em `src/shared/infra` (ADR-0025, item 4) e binding `UnitOfWork → PrismaUnitOfWork`.
- **Exceção de infra `OptimisticLockException`** + conversão para `ConcurrencyError` (se o ADR-0030 confirmar).
- Atualizar [04-cqrs-and-events.md](../../architecture/04-cqrs-and-events.md) (assinatura final), `src/shared/infra/AGENTS.md` e a skill de Command, se já existir em `.agents/skills/`.

## Critérios de aceite
- [ ] int: `execute` que salva uma linha de teste e adiciona um Integration Event, e depois lança exceção, não deixa **nem** a linha **nem** o outbox (rollback atômico).
- [ ] int: `execute` cujo `work` devolve `Left` não persiste nada e devolve o mesmo `Left` (se o ADR-0030 confirmar a recomendação 2).
- [ ] int: um handler de Domain Event registrado no dispatcher escreve na mesma transação. Se o handler falhar, o efeito do `work` também é desfeito.
- [ ] int: um handler que gera um novo Domain Event em outro agregado rastreado tem esse evento despachado (laço de re-dispatch); um laço infinito estoura o limite com erro claro.
- [ ] int: com `tenantId = <org A>` no contexto, `current_setting('app.current_tenant_id', true)` dentro do `work` é `<org A>`; numa transação seguinte, sem tenant, **não** é (prova do escopo `LOCAL`, ADR-0017 regra 3). Com `runAsSystem`, o valor é `SYSTEM_BYPASS`.
- [ ] int: a linha do outbox tem `id` UUIDv7, `payload` igual ao envelope completo validado pelo contrato (`correlationId` e `actor` do contexto, `schemaVersion` do contrato) e `status = 'PENDING'`.
- [ ] int: um cliente `pg` com `LISTEN outbox_new_event` recebe a notificação **só depois** do commit, e não recebe nada num rollback.
- [ ] int: `payload` que não passa no `contract.payloadSchema` faz rollback e lança erro de programação (não é `Left`).
- [ ] int: `execute` aninhado faz commit uma única vez (conforme o ADR-0030).
- [ ] `pnpm arch:check` verde (`application/` não importa `infra/`).
- [ ] `pnpm verify` passa; `pnpm test:int` verde.

## Notas / riscos
- A ordem dentro da transação é fixa: `set_config` → `work` → laço de dispatch → outbox → `pg_notify` → commit. Mudar a ordem quebra o ADR-0009 (handlers precisam ver o tenant) ou o ADR-0007.
- O timeout padrão da transação interativa do Prisma (5 s) pode estourar em handlers pesados. Torne-o configurável por env só se um teste exigir.
- Se esta task passar de ~400 linhas, quebre o envelope e outbox numa `T3.05d` e atualize o ROADMAP.
