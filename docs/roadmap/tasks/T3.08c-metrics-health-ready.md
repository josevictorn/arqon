## Objetivo
`GET /metrics` expõe, no formato Prometheus, as métricas padrão do Node e a latência HTTP por rota template. `GET /health/ready` responde `200` só quando PostgreSQL, MongoDB e Redis respondem dentro de um timeout, e `503` com o detalhe de cada dependência quando algum falha. Outras partes do sistema (resiliência, Outbox, Kafka) conseguem registrar métricas e checagens novas sem alterar estes controllers.

## Escopo
- **Dependência:** `prom-client` (versão exata).
- **`src/shared/infra/observability/metrics/`**:
  - `MetricsRegistry`: provider singleton com o `Registry` do `prom-client`, `collectDefaultMetrics` e prefixo derivado de `APP_SLUG` (ADR-0012);
  - `http_server_request_duration_seconds` (histogram), com labels `method`, `route` (template), `status_code`, gravado no mesmo ponto da linha canônica (T3.08a). Proibido usar a URL crua como label;
  - `MetricsController` com `GET /metrics` (`text/plain; version=0.0.4`), excluído do OpenAPI e do rate limit (o `@SkipRateLimit` chega na T3.09; deixe anotado).
- **Readiness** (`src/shared/infra/http/health/`):
  - abstract class `HealthIndicator` (`name`, `check(): Promise<void>`) + token multi-provider para registro;
  - indicadores `postgres` (`SELECT 1`), `mongodb` (`ping`) e `redis` (`PING`), cada um com timeout próprio (env `HEALTH_CHECK_TIMEOUT_MS`, default `1000`);
  - `GET /health/ready` → `200 { status: "ok", checks: { postgres: "up", … } }` ou `503 { status: "error", checks: { …, redis: "down" } }`, executando as checagens **em paralelo**. O corpo do 503 não expõe mensagem de erro do driver (pode conter host ou credencial);
  - `/health/live` continua sem tocar em dependências.
- `.env.example` e `EnvModule`: `HEALTH_CHECK_TIMEOUT_MS`.
- Atualizar [09-observability.md](../../architecture/09-observability.md) e `src/shared/infra/AGENTS.md` (como registrar métrica e `HealthIndicator` novos).

## Critérios de aceite
- [ ] e2e: `GET /metrics` responde `200` com `process_cpu_user_seconds_total` (ou equivalente do prefixo) e, após um `GET /test/items/:id`, uma série de `http_server_request_duration_seconds_bucket` com `route="/test/items/:id"` (template, sem o ID).
- [ ] e2e: com a infra `core` de pé, `GET /health/ready` responde `200` com os 3 checks `up`.
- [ ] e2e/int: com um `HealthIndicator` de Redis apontando para uma porta fechada (override no módulo de teste), `GET /health/ready` responde `503`, `redis: "down"`, o corpo sem mensagem do driver, e responde dentro de `HEALTH_CHECK_TIMEOUT_MS` + margem.
- [ ] e2e: `GET /metrics` e `GET /health/ready` 200 não geram linha de log (T3.08a); o 503 gera.
- [ ] `GET /health/live` continua `200` mesmo com as dependências fora.
- [ ] `pnpm verify` passa; `pnpm test:e2e` verde.

## Notas / riscos
- O `prom-client` usa um registry global por padrão. Use um `Registry` próprio injetado, senão testes que sobem o app várias vezes acusam "metric already registered".
- O timeout de cada check precisa cancelar ou ignorar a promise pendente sem deixar *unhandled rejection*.
