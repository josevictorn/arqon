## Objetivo
O `detail` de todo Problem Details sai traduzido conforme o `Accept-Language` (`pt-BR` ou `en`, com fallback `en`), interpolando os `args` do `DomainError`. Um teste impede o merge de qualquer `i18nKey` sem tradução nos dois idiomas, ou com placeholders diferentes entre eles.

## Escopo
- **Dependência:** `nestjs-i18n` (versão exata compatível com Nest 11).
- **`src/shared/infra/i18n/`**: `I18nConfigModule` com `AcceptLanguageResolver`, `fallbackLanguage: "en"` e `fallbacks` (`pt*` → `pt-BR`, `en*` → `en`).
- **Dicionários:** `src/shared/infra/i18n/locales/{en,pt-BR}/errors/common.json` (organização por contexto, para que a chave `errors.common.resource_not_found` resolva para o arquivo `errors/common.json`). Chaves: todas as `errors.common.*` que já existem no código (`resource_not_found`, `not_allowed`, `invalid_id`, `invalid_event_name`, `concurrency_conflict`, `route_not_found`, `validation_failed`) e a do `500` (`internal_error`).
- **`NestI18nErrorMessageTranslator`**: implementa a porta da T3.02 e é registrado no lugar da implementação padrão.
- **Build:** `nest-cli.json` copia os `.json` de `locales` para o `dist` (`assets` + `watchAssets`); `pnpm build && pnpm start` resolve as traduções.
- **`src/shared/infra/i18n/locales.spec.ts`** (unit), que garante:
  1. `en` e `pt-BR` têm **exatamente** o mesmo conjunto de chaves (achatadas);
  2. cada `i18nKey: "errors.…"` literal em `src/**/*.ts` (fora de specs) existe nos dois idiomas;
  3. os placeholders (`{feature}`, `{limit}`…) de cada chave são os mesmos nos dois idiomas.
- Atualizar o `src/shared/infra/AGENTS.md` (onde ficam os dicionários, regra de paridade) e o [07-i18n-and-errors.md](../../architecture/07-i18n-and-errors.md).

## Critérios de aceite
- [ ] e2e: o mesmo `Left(ResourceNotFoundError)` responde `detail` em português com `Accept-Language: pt-BR`, em inglês com `en`, e em inglês sem header ou com `Accept-Language: fr`.
- [ ] e2e: `Accept-Language: pt` (sem região) resolve para `pt-BR`.
- [ ] e2e: os `args` aparecem interpolados no `detail` (ex.: o `resource` e o `id` do `ResourceNotFoundError`).
- [ ] `locales.spec.ts` falha (prova manual descrita no PR) se uma chave existir só em `en`, se um `i18nKey` do código não tiver tradução, ou se um placeholder divergir entre os idiomas.
- [ ] `pnpm build && pnpm start` sobe e responde um erro traduzido (as traduções estão no `dist`).
- [ ] `pnpm verify` passa; `pnpm test:e2e` verde.

## Notas / riscos
- Confirme se a versão do `nestjs-i18n` mapeia subpastas para prefixo de chave (`en/errors/common.json` → `errors.common.*`). Se não mapear, use `en/errors.json` com objetos aninhados por contexto e **corrija o caminho citado no [iam/spec.md](../../modules/iam/spec.md)** no mesmo PR.
- O teste de paridade lê o código-fonte com regex. Mantenha os `i18nKey` como literais de string (não monte a chave dinamicamente), senão o teste não os enxerga.
- `DomainErrorArgs` aceita `null`. Defina o que a interpolação mostra para `null` e cubra com teste.
