# T3.05b — `RequestContext` (`AsyncLocalStorage`) + correlation id por requisição

- **Fase:** F3 — `src/shared/infra` (plataforma)
- **Status:** 📝 Detalhada
- **Depende de:** T3.02
- **ADRs:** [0009](../../decisions/0009-domain-events-e-unit-of-work.md), [0013](../../decisions/0013-estrategia-de-logging-canonical-logs-e-custo.md), [0016](../../decisions/0016-resolucao-tenant-ativo-por-requisicao.md), [0019](../../decisions/0019-envelope-integration-event.md)
- **Branch:** `task/T3.05b-request-context-als`
- **Tamanho esperado:** P

## Objetivo
Toda unidade de trabalho (requisição HTTP agora; mensagem Kafka e job a partir da F4) roda dentro de um `RequestContext` em `AsyncLocalStorage` com `correlationId`, `actor` e `tenantId`. É a fonte única de onde o `UnitOfWork` (T3.05c) preenche o envelope e de onde o canonical log (T3.08a) tira `tenantId`/`userId`. Requisições concorrentes nunca enxergam o contexto umas das outras.

## Escopo
- **Porta `RequestContextPort`** (abstract class, em `src/shared/application/`), para use cases e infra: leitura de `correlationId`, `tenantId`, `actor`, e `setTenant(organizationId)` / `setActor(actor)` (usados pelos guards na T5.06).
- **`AlsRequestContext`** (`src/shared/infra/context/`): implementação com `AsyncLocalStorage` nativo (`node:async_hooks`), sem `nestjs-cls`, e com:
  - `run(initial, fn)` para abrir um contexto (HTTP, consumer, cron);
  - `runAsSystem(fn)` para workers e jobs (`actorType: "SYSTEM"`, `tenantId: null`), já pronto para a F4.
- **Fronteira HTTP:** hook do Fastify (ou middleware do Nest, o que preservar o contexto até o controller; escolha justificada no PR) que abre o contexto com:
  - `correlationId` do header `x-correlation-id` quando for válido (≤ 128 chars, `[A-Za-z0-9._-]`), senão um UUIDv7 novo;
  - `actor = { actorType: "ANONYMOUS", actorId: null, ipAddress: request.ip, userAgent }`;
  - `tenantId = null`;
  - header de resposta `x-correlation-id` ecoando o valor.
- O `GlobalDomainExceptionFilter` (T3.02) passa a preencher `correlationId` no Problem Details.
- Atualizar `src/shared/infra/AGENTS.md` (nunca ler tenant do body/JWT; quem escreve no contexto).

## Fora de escopo
- Resolver o tenant por `:orgId` / `X-Organization-Id` e o usuário pelo JWT (→ T5.06). Aqui o contexto só oferece `setTenant`/`setActor`.
- Preenchimento do envelope e `set_config` do tenant (→ T3.05c).
- `LogContextPort` e campos extras da linha canônica (→ T3.08a). Se fizer sentido, o mesmo store do ALS pode carregar um mapa de atributos de log, mas a porta e o uso ficam para a T3.08a.
- Contexto de consumer Kafka (→ T4.04/T4.05, que usam `run`/`runAsSystem`).

## Critérios de aceite
- [ ] e2e (controller de teste): o `correlationId` lido via `RequestContextPort` dentro de um serviço injetado é o mesmo do header de resposta `x-correlation-id`.
- [ ] e2e: um `x-correlation-id` válido enviado é ecoado; um inválido (ex.: 500 chars ou com espaço) é trocado por um UUIDv7.
- [ ] Unit: 50 execuções concorrentes de `run` com `await` intercalado (`setTimeout`/`Promise`) leem cada uma o seu próprio `correlationId` e `tenantId`.
- [ ] Unit: fora de qualquer `run`, ler o contexto devolve um valor explícito (`undefined` ou um erro de programação documentado) e nunca o contexto de outra execução.
- [ ] Unit: `runAsSystem` produz `actor.actorType === "SYSTEM"` e `tenantId === null`.
- [ ] e2e: o Problem Details de um erro contém o mesmo `correlationId` do header.
- [ ] `pnpm verify` passa; `pnpm test:e2e` verde.

## Notas / riscos
- `AsyncLocalStorage.enterWith` vaza contexto entre requisições em alguns fluxos. Prefira `run(store, next)` e prove com o teste de concorrência.
- `request.ip` só reflete o cliente real com `TRUST_PROXY` correto (T3.02). Não leia `x-forwarded-for` à mão.
- `ipAddress` e `userAgent` são dados pessoais. Eles vão para o envelope (ADR-0019) e não devem ir para o `payload` nem para logs além do que o ADR-0013 permite.
