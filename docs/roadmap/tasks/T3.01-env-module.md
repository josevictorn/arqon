# T3.01 — `EnvModule` (Zod) com falha rápida no boot

- **Fase:** F3 — `src/shared/infra` (plataforma)
- **Status:** 📝 Detalhada

- **Tamanho esperado:** M

## Objetivo
A API só sobe com variáveis de ambiente válidas: um env inválido encerra o processo antes do Nest, com exit code `1` e uma linha `fatal` que lista **as chaves** inválidas (nunca os valores). Todo código de `src/` lê configuração tipada de um `EnvService` injetável, nunca de `process.env`.

## Escopo
- **`src/shared/infra/config/env.schema.ts`**: schema Zod (`z.object`) com as variáveis que a F3 usa, com coerção e defaults:
  - App: `NODE_ENV` (`development | test | production`), `PORT` (int 1–65535, default `3000`), `APP_NAME` (string não vazia), `APP_SLUG` (`^[a-z][a-z0-9-]*$`), `CORS_ORIGINS` (lista separada por vírgula → `string[]` de URLs).
  - Dados: `DATABASE_URL` (`postgresql://`), `MONGODB_URI` (`mongodb://` ou `mongodb+srv://`), `REDIS_URL` (`redis://` ou `rediss://`).
  - Logs e OTel: `LOG_LEVEL` (`debug | info | warn | error | fatal | silent`), `LOG_READ_SAMPLE_RATE` (número em `[0, 1]`), `LOG_SLOW_THRESHOLD_MS` (int `> 0`), `OTEL_SERVICE_NAME`, `OTEL_EXPORTER_OTLP_ENDPOINT` (URL).
  - Tipo exportado `Env = z.infer<typeof envSchema>`.
- **`src/shared/infra/config/load-env.ts`**: `parseEnv(source: NodeJS.ProcessEnv): Either<EnvValidationIssue[], Env>` (pura, testável) + carregamento do `.env` local quando existir, sem dependência `dotenv` (`process.loadEnvFile`, Node 24) e **sem sobrescrever** variáveis já definidas no ambiente.
- **`EnvModule` (`@Global()`) + `EnvService`** com `get<K extends keyof Env>(key: K): Env[K]` e o env validado congelado (`Object.freeze`).
- **`src/main.ts`**: valida o env **antes** de `NestFactory.create`; em falha, escreve no `stderr` um JSON `{ level: "fatal", event: "app.bootstrap.env_invalid", issues: [{ key, message }] }` e encerra com `process.exitCode = 1`. A porta passa a vir do `EnvService`.
- **Testes:** `NODE_ENV=test` e `LOG_LEVEL=silent` como defaults de `test/setup-{int,e2e}.ts`.
- Atualizar `.env.example` se faltar alguma chave do schema (o `test/infra/local-infra.spec.ts` continua verde).

## Fora de escopo
- Variáveis de Kafka/Schema Registry (→ T4.01), JWT/MFA (→ T5.01), S3 e SMTP (→ T5.02/T5.03), pagamentos (→ T5.04), Outbox (`OUTBOX_*`, `RUN_WORKERS_IN_API` → T4.03). Cada task acrescenta as suas ao schema.
- Variáveis novas das próximas tasks da F3 (`TRUST_PROXY`, `API_DOCS_ENABLED`, `RATE_LIMIT_*` etc.): cada uma entra na task que a usa.
- Logger Pino (→ T3.08a): a linha `fatal` de env inválido é escrita direto no `stderr`, porque o logger ainda não existe nesse ponto do boot.
- `@nestjs/config`: não adicionar. O `EnvService` próprio basta e evita uma camada de `ConfigService` sem tipo.

## Critérios de aceite
- [ ] Unit: `parseEnv` devolve `Right` para o `.env.example` e `Left` com a **chave** (sem o valor) para `PORT=abc`, `APP_SLUG=Arqon`, `DATABASE_URL=mysql://x` e `LOG_READ_SAMPLE_RATE=2`.
- [ ] Unit: `CORS_ORIGINS="http://a.test, http://b.test"` vira `["http://a.test", "http://b.test"]`; `PORT` ausente vira `3000`.

## Notas / riscos
- Confirmar no Node 24 se `process.loadEnvFile` preserva as variáveis já definidas no ambiente. Se não preservar, faça o merge à mão (ambiente > arquivo). O CI usa `cp .env.example .env`, então os dois caminhos precisam funcionar.
- `parseEnv` devolve `Either` por consistência, mas é erro de **boot**, não de negócio: quem chama (o `main.ts`) encerra o processo.
- Não exponha o `Env` inteiro em logs nem em respostas HTTP. Ele contém segredos a partir da F5.
