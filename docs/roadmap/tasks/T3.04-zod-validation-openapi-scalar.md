# T3.04 — Validação Zod (`nestjs-zod`) + OpenAPI + Scalar em `/docs`

- **Fase:** F3 — `src/shared/infra` (plataforma)
- **Status:** 📝 Detalhada
- **Depende de:** T3.02, T3.03
- **ADRs:** [0003](../../decisions/0003-runtime-versoes-e-package-manager.md), [0012](../../decisions/0012-inicializacao-de-novos-projetos.md), [0014](../../decisions/0014-identificadores-uuidv7.md) (+ formato do ADR-0029)
- **Branch:** `task/T3.04-zod-validation-openapi-scalar`
- **Tamanho esperado:** M

## Objetivo
Um único schema Zod por DTO valida o request (body, query e params) e gera a documentação: um request inválido recebe `400` em Problem Details com a lista de issues, e `GET /docs` serve o Scalar API Reference com o OpenAPI gerado, com título vindo de `APP_NAME`, Bearer Auth e o schema de erro documentado.

## Escopo
- **Dependências:** `nestjs-zod` 5.x, `@nestjs/swagger` (exigido pelo `nestjs-zod` para gerar o documento) e `@scalar/nestjs-api-reference`, com versões exatas.
- **Validação global:** `ZodValidationPipe` como `APP_PIPE`. O filtro da T3.02 mapeia `ZodValidationException` para `400` `COMMON.VALIDATION_FAILED`, com `detail` traduzido e `errors: [{ path, code, message }]` (`path` em dot-notation, `code` = código da issue do Zod).
- **`src/shared/infra/http/validation/`**: `uuidV7Schema` (`z.uuid({ version: "v7" })`) para params e corpo, que é o item que a T2.02 deixou para cá.
- **OpenAPI** (`src/shared/infra/http/openapi/`):
  - `DocumentBuilder` com `title = APP_NAME`, `version` do `package.json`, `addBearerAuth()` e `addApiKey` para o header `X-Organization-Id` (ADR-0016);
  - `cleanupOpenApiDoc` do `nestjs-zod`;
  - componente `ProblemDetails` (e `ValidationProblemDetails`) registrado e usado como resposta padrão de erro;
  - JSON do documento em `GET /docs/openapi.json`.
- **Scalar** em `GET /docs`, com `withFastify` e a CSP do Helmet liberada **só** nessa rota (a CSP global da T3.02 continua igual).
- **Env nova:** `API_DOCS_ENABLED` (boolean; default `true`, exceto quando `NODE_ENV=production`, em que o default é `false`) no `EnvModule` e no `.env.example`.
- Atualizar o [08-api-docs.md](../../architecture/08-api-docs.md) e o `src/shared/infra/AGENTS.md` (como declarar DTOs e respostas de erro).

## Fora de escopo
- DTOs e rotas de módulos de negócio (→ F6+).
- Serialização/validação de **resposta** com `ZodSerializerDto`: deixe anotado em Follow-ups se fizer sentido.
- Tradução de cada `message` das issues do Zod por idioma: o `detail` é traduzido (T3.03), e as `message` das issues seguem as do Zod. Se precisar traduzir, abra uma task/ADR.
- Geração de clientes HTTP ou publicação do OpenAPI no CI.

## Critérios de aceite
- [ ] e2e (controller de teste em `test/`): `POST` com body inválido responde `400` `COMMON.VALIDATION_FAILED`, com `errors[].path` apontando os campos e `detail` traduzido conforme o `Accept-Language`.
- [ ] e2e: param `:id` com UUIDv4 é rejeitado com `400`; UUIDv7 passa.
- [ ] e2e: `GET /docs` responde `200` `text/html` e `GET /docs/openapi.json` tem `info.title === process.env.APP_NAME`, o security scheme `bearer` e o componente `ProblemDetails`.
- [ ] e2e: com `API_DOCS_ENABLED=false`, `GET /docs` responde `404` (Problem Details).
- [ ] e2e: a CSP de `GET /health/live` é a mesma de antes da task (a liberação vale só para `/docs`).
- [ ] O DTO de teste não tem nenhum decorator `@ApiProperty`: o schema vem só do Zod.
- [ ] `pnpm verify` passa; `pnpm test:e2e` verde.

## Notas / riscos
- O `nestjs-zod` 5 mudou a API em relação ao 3/4 (`createZodDto`, `cleanupOpenApiDoc`, `ZodValidationPipe`). Siga a documentação da versão instalada, não exemplos antigos.
- `import type` em DTOs usados como parâmetro de controller quebra a metadata (armadilha do AGENTS.md): use import de valor.
- `z.toJSONSchema` do Zod 4 e o gerador do `nestjs-zod` podem divergir em `.describe()` e `.optional()`. Confira o JSON gerado no teste, não só o status `200`.
