## Pergunta que bloqueia (vira o ADR-0031)
O compose sobe o PostgreSQL com `POSTGRES_USER=postgres`, que é **superusuário**, e superusuário **ignora RLS** mesmo com `FORCE ROW LEVEL SECURITY`. Se a API usar esse papel, a camada 3 do ADR-0017 não protege nada e a suíte cross-tenant da T8.06 passaria por acaso. **Recomendação:** dois papéis:
- **owner/migrations** (o `postgres` atual), usado só por `prisma migrate`, via `DATABASE_MIGRATION_URL`;
- **runtime** (`${APP_SLUG}_app`, `NOSUPERUSER NOBYPASSRLS`, com `GRANT` de DML nas tabelas), usado pela API e pelos workers via `DATABASE_URL`, criado por um script de init do compose.

Workers internos continuam usando o `SYSTEM_BYPASS` da policy (ADR-0017), não um papel com `BYPASSRLS`.

## Escopo
- **Dependências:** `prisma` (dev) e `@prisma/client` 7.x + `@prisma/adapter-pg` + `pg`, todos com versão exata.
- **`prisma.config.ts`** + **`prisma/schema.prisma`** com o generator `prisma-client` (saída CommonJS num diretório gerado e ignorado pelo git, por Biome, `tsc` e coverage), e o script `pnpm db:generate` acionado antes de `typecheck`/`build`/testes (ex.: `postinstall`).
- **Model `OutboxEvent` → `outbox_events`** com as colunas do ADR-0007: `id` (`@db.Uuid`, = `eventId`, sem default), `aggregate_id` (`@db.Uuid`), `topic`, `event_version` (int), `payload` (`jsonb`, o **envelope completo** do ADR-0019), `headers` (`jsonb`), `status` (enum `PENDING | PUBLISHED | FAILED`, default `PENDING`), `attempts` (default `0`), `last_error`, `next_attempt_at` (default `now()`), `occurred_at`, `published_at`.
- **Migration inicial** com SQL manual para o índice parcial `idx_outbox_pending ON outbox_events (next_attempt_at, occurred_at) WHERE status = 'PENDING'` e o `GRANT` ao papel de runtime. `outbox_events` **não** tem `organization_id` nem RLS: o relay lê tudo, e o tenant fica dentro do envelope.
- **Papéis (conforme o ADR-0031):** script de init em `docker/postgres/` que cria o papel de runtime a partir das envs; `.env.example` com `DATABASE_URL` (runtime) e `DATABASE_MIGRATION_URL` (owner); scripts `pnpm db:migrate` (dev) e `pnpm db:deploy` (CI/produção). O `scripts/init-project.ts` e o teste dele são atualizados se algum arquivo novo da raiz carregar o slug (ADR-0012, regra 3).
- **`src/shared/infra/database/prisma/`**: `PrismaService` (adapter `pg`, `onModuleInit` conecta e `onModuleDestroy` desconecta) e `PrismaModule` (`@Global()`). O getter `client`, que na T3.05c passa a devolver o `tx` do ALS, por ora devolve o client raiz.
- **Isolamento de integração (PostgreSQL)** em `test/support/postgres.ts`, chamado pelo `test/setup-int.ts`: cada worker do Vitest cria o schema `test_<worker>_<uuid>`, roda `prisma migrate deploy` nele, aponta o `DATABASE_URL` para ele (`?schema=`) e o remove ao final.
- CI: `pnpm db:deploy` antes de `test:int`/`test:e2e`, se o isolamento não cobrir o e2e (o e2e ganha isolamento por arquivo na T3.11).
- Atualizar `src/shared/infra/AGENTS.md` (Prisma: IDs sem default, toda tabela com `organization_id` exige RLS) e [10-testing.md](../../architecture/10-testing.md).

## Critérios de aceite
- [ ] `pnpm infra:reset && pnpm infra:up && pnpm db:deploy` cria `outbox_events` com as colunas do ADR-0007 e o índice parcial (verificável por `\d outbox_events`).
- [ ] int: `SELECT rolsuper, rolbypassrls FROM pg_roles WHERE rolname = current_user` com o `DATABASE_URL` da aplicação devolve `false, false`.
- [ ] int: com o papel de runtime, uma tabela temporária de teste com `FORCE ROW LEVEL SECURITY` e a policy do ADR-0017 não devolve linhas sem `set_config`. Isso prova que a camada 3 funciona com esse papel.
- [ ] int: o `PrismaService` insere e lê um `OutboxEvent` com `id` UUIDv7 gerado por `UniqueEntityID`.
- [ ] int: dois arquivos `*.int-spec.ts` rodando em paralelo usam schemas diferentes (o teste lê `current_schema()`), e o schema é removido no fim.
- [ ] `grep -rn "@default(uuid\|autoincrement" prisma` não encontra nada.
- [ ] `pnpm verify` passa; `pnpm test:int` verde no CI.

## Notas / riscos
- O Prisma 7 exige *driver adapter* e `prisma.config.ts`, e a URL não fica mais no `schema.prisma`. Siga a documentação do 7.x; exemplos do Prisma 5/6 não servem.
- `pnpm infra:reset` é necessário para o script de init do PostgreSQL rodar, porque ele só roda com volume vazio. Avise no PR e no README (Troubleshooting).
- O código gerado do Prisma não pode entrar no `arch:check` nem no coverage. Confirme as exclusões no `.dependency-cruiser.cjs` (`exclude`, sem regra nova) e no `vitest.config.mts`.
